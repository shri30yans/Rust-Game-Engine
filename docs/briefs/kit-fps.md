# kit-fps: first-person controller, health, hitscan weapons and bots (build step 3, `kits/fps`)

Goal: a new optional kit crate `kits/fps` (package `kit-fps`) holding the genre gameplay a first-person shooter needs, with NO game names and every number in config structs passed in by the game: (1) a first-person character controller with real jumping, (2) health and damage, (3) a hitscan weapon with ammo, reload and spread, (4) bots that see, chase, aim and shoot back, using the same command type as the player. Everything runs inside the deterministic simulation (no wall clock, no thread RNG; randomness only from `core::SimRng` passed in or stored in a world resource). Done means: all the pure logic is unit and property tested; a headless scripted test proves a bot kills a stationary player and a player kills a bot; the four gates pass. No game crate is touched in this brief (the game comes next).

Read first: `AGENTS.md`, `docs/ARCHITECTURE.md` §0-1 and §166 (kits), `docs/README.md` §7 D24, D36, D37, `games/sandbox/game/src/sim.rs` (the existing character system; it is the reference for how a kinematic capsule is driven through `engine-physics`; do NOT depend on or edit the sandbox), `engine/physics/src/{world,character}.rs`, `engine/core/src/rng.rs`, `engine/world/src/{world,resource}.rs`, `engine/app/src/{config,client}.rs`.

## Setup
`kits/fps/Cargo.toml` (package `kit-fps`, workspace member, depends on `core`, `world`, `physics`, `glam`, `thiserror` as the sandbox does; no new external dependencies, dev-dep `proptest` if already in the workspace). Add `{ "pattern": "kits/*", "layer": 5 }` to `tools/check-layers/layers.json` and make `cargo run -p check-layers` pass (kits may use engine crates and other kits only).

## 1. Controller (`src/controller.rs`)
Pure maths first, then a system.
- `ControllerConfig { walk_speed, ground_accel, ground_friction, air_accel, air_speed_cap, jump_speed, gravity, max_fall_speed, coyote_ticks: u32, jump_buffer_ticks: u32, jump_cut: f32 (0..1, multiplier on upward speed when the jump button is released early), step_height, slope_limit }` validated by `ControllerConfig::new(...) -> Result<_, KitError>` (all finite, positive where needed, `jump_cut` in [0,1]).
- `MoveCommand { move_axis: Vec2 (strafe, forward, each clamped to [-1,1] by construction), view: ViewAngles, jump_pressed: bool (edge this tick), jump_held: bool, fire: bool, reload: bool }` is THE command type for player and bots (typed, validated constructor). The game's input maps onto it.
- `pub fn step_velocity(state: &mut LocomotionState, cfg: &ControllerConfig, cmd: &MoveCommand, grounded: bool, dt: f32) -> Vec3` pure: ground acceleration toward the wished velocity with friction, air control (accelerate in air with `air_accel`, capped by `air_speed_cap`), gravity, terminal fall speed, **coyote time** (jump allowed for `coyote_ticks` after leaving the ground), **jump buffering** (a jump press up to `jump_buffer_ticks` before landing fires on landing), **variable jump height** (releasing jump while rising multiplies upward speed by `jump_cut` once). `LocomotionState` holds vertical speed, coyote and buffer counters, a `jumped` latch.
- A world system `locomotion_system` (a `fn(&mut World, &mut SystemContext)`) that, for every entity with `Locomotion` (state + config handle + body id + `MoveCommand`), calls `step_velocity` and moves the body with `physics::CharacterController::move_character` exactly as the sandbox does, writing the entity `Transform` from the body. Component and resource layout follows D36/D37: the physics world is a resource.
Tests: ground accel reaches walk speed and no more; friction stops; jump height with hold equals `v^2 / 2g` within 1 percent and a quick tap reaches about `jump_cut` squared of that; coyote jump works within the window and not after; buffered jump fires on landing; air control cannot exceed the cap; terminal velocity; proptest that speed never exceeds `max(walk_speed, air cap, jump speed, max_fall_speed)` plus epsilon for random command sequences; a physics-backed test (a capsule on a floor with a 1 m wall) that jumps onto a 1.5 m box using held jump and cannot with a tap.

## 2. Health and damage (`src/health.rs`)
`Health { current: u32, max: u32 }` with `Damage(u32)`; `Health::apply(&mut self, Damage) -> Outcome::{Survived{remaining}, Died}`, saturating, no negative; `Team(u8)`; `Alive` is derived from `current > 0`, not a flag. A `DamageEvent { target: NetId, source: NetId, amount: Damage }` queue as a world resource `DamageLog` (cleared each tick by the system that drains it) so the game can show hit markers and kill feeds. Tests including a proptest that health never exceeds max and never underflows.

## 3. Weapons (`src/weapon.rs`)
`WeaponConfig { damage, fire_interval_ticks, magazine, reload_ticks, spread_rad (full cone, grows by `spread_per_shot` and recovers by `spread_recovery_per_tick`), max_range, pellets: u32 (1 for a rifle) }` validated; `WeaponState { ammo, cooldown, reload_left, spread }`; pure `WeaponState::tick(&mut self, cfg, fire: bool, reload: bool, rng: &mut SimRng) -> Option<Shot>` where `Shot { directions: ArrayVec-free: a fixed `[Vec3; MAX_PELLETS]` plus `count` }` (const `MAX_PELLETS = 12`, no allocation) built from the view direction with spread sampled uniformly in the cone. A `weapon_system` resolves each shot with `PhysicsWorld::ray_cast` from the eye, ignoring the shooter's own body (use the exclude facility the physics crate already has; if ray_cast has no exclusion, add the minimal additive `ray_cast_excluding` to `engine-physics` with tests, same style as `intersects_shape_excluding`), and on a hit whose collider belongs to an entity with `Health` and a different `Team`, pushes a `DamageEvent` (friendly fire off by default via config). A `damage_system` drains `DamageLog` into `Health`, and a dead entity's `Locomotion` command is ignored. Tests: fire rate (shots in N ticks), magazine and reload timing, cooldown, spread stays within the cone (proptest) and the cone grows then recovers, deterministic for equal seeds, no allocation per tick (counting-allocator test, one `#[test]` per file as the other crates do).

## 4. Bots (`src/bot.rs`)
`BotConfig { sight_range, fov_rad, reaction_ticks, aim_speed_rad_per_s, aim_error_rad (starting error, shrinks while the target stays visible), engage_range, stop_distance, strafe_period_ticks, turn_speed, forget_ticks }` validated. `Bot` state machine `Idle -> Patrol(waypoint) -> Chase -> Attack`, losing sight for `forget_ticks` returns to Patrol. Perception: field of view and range test plus a line-of-sight ray to the target's eye (the ray must reach the target collider first). Aiming: the bot's view turns toward the target at `aim_speed` with the current aim error offset; it fires only when the angle to the target is below a threshold AND the reaction delay has elapsed since first sighting. Movement: seeks a target position (the target in Chase, a strafe offset in Attack, the next waypoint in Patrol) with a simple obstacle test using `shape_cast` forward (turn away when blocked, jump if a low obstacle blocks and the controller can clear it); NO navmesh in this brief, waypoints come from the game as `Vec<Vec3>` in a `Waypoints` resource (validated non-empty when any bot exists). The bot outputs a `MoveCommand`, so it uses `locomotion_system` and `weapon_system` like the player. A `bot_system` runs before them. All decisions use only world state and a per-bot `SimRng` fork (`rng.fork(bot_index)`), so replays match. Tests: pure state transitions with a scripted perception stub (trait `Senses` implemented by the real physics-backed senses and by a test fake), reaction delay respected, aim error shrinks while visible, forgets after `forget_ticks`, never fires without line of sight; and the integration test below.

## 5. Integration test (`tests/duel.rs`)
Build a small scene in the test (floor, one wall, physics resource, two capsule bodies) with: a stationary player entity (Health 100, Team 0) and a bot (Team 1) with a rifle; run the schedule for at most 20 simulated seconds; assert the player dies, the `DamageLog` shows only damage from the bot, and the whole run is identical for equal seeds (compare `world.state_hash()` across two runs; make `Health`, `WeaponState` and bot state hash into the world through the resource/component hashing the world crate defines). A second test: a scripted player command stream aims and fires at a stationary bot (Team 1, no `bot_system`) and kills it in the expected number of ticks given damage and fire rate. A third: a wall between them, the bot never fires.

## Errors
One `KitError` (thiserror) with typed variants for invalid configs and for world/physics failures carrying the source (`#[from]`, do not discard errors, no `map_err(|_| ...)`). If a needed `WorldError`/`PhysicsError` conversion is missing, add the narrowest `#[from]` variant in the owning crate (additive).

## Do not
Name a game, mode, map or weapon in the kit (a weapon is data). Edit the sandbox or the render crate. Add dependencies not already in the workspace. `#[allow]` in non-test code, `unwrap`, `expect`, `unwrap_or*`, `.ok()`, `let _ =`, panicking indexing, truncating `as` casts, stubs, dead code. Claim performance without a test.
